# 办公区灯控技术方案

## 1. 总体架构
本方案采用 **BLE Mesh + MQTT + Vue** 的三层结构：

- **终端层**：3 块开发板作为灯控节点
  - 1 块 ESP32-WROOM：D2 单色 LED
  - 2 块 ESP32-S3：GPIO48 WS2812 RGB
- **网关层**：1 个主节点/网关负责汇总状态、接收 MQTT、转发 BLE Mesh 指令
- **业务层**：MQTT 服务器 + Vue 管理界面

```
Vue
 ↓
MQTT Server
 ↓
Gateway / Root Node
 ↓
BLE Mesh
 ↓
WROOM D2 / S3 WS2812 nodes
```

## 2. 节点角色设计
### 2.1 Root / Gateway
职责：
- 连接 MQTT 服务器
- 接收前端控制命令
- 汇总节点状态
- 处理节点掉线和重选主
- 对外暴露统一设备视图

### 2.2 普通灯控节点
职责：
- 执行开关灯、亮度、颜色、闪烁等动作
- 周期性上报心跳与状态
- 失去父节点后自动重连

## 3. 硬件映射
### 3.1 WROOM 节点
- 物理灯：D2 单色 LED
- 状态表达：
  - 常亮 = 在线
  - 慢闪 = 接收到命令
  - 快闪 = 断链/告警

### 3.2 S3 节点
- 物理灯：GPIO48 WS2812 RGB
- 状态表达：
  - RGB 颜色表示层级/房间/场景
  - 颜色变化表示命令执行成功
  - 红色闪烁表示故障

## 4. 协议设计
### 4.1 BLE Mesh 侧
建议定义三类消息：
- `STATUS`：节点状态上报
- `CMD`：开关/亮度/颜色控制
- `HEARTBEAT`：在线心跳

### 4.2 MQTT 侧
#### Topic 规划
- `office/light/gateway/status`
- `office/light/gateway/event`
- `office/light/node/{id}/status`
- `office/light/node/{id}/event`
- `office/light/node/{id}/cmd`
- `office/light/scene/cmd`

#### Payload 示例
```json
{
  "device_id": "node-001",
  "online": true,
  "role": "node",
  "type": "wroom",
  "layer": 2,
  "state": "on",
  "brightness": 80,
  "color": "#FFCC00",
  "ts": 1710000000
}
```

## 5. 状态机
### 5.1 节点状态
- `INIT`
- `JOINING`
- `ONLINE`
- `FOLLOWER`
- `ROOT`
- `DISCONNECTED`
- `RECOVERING`

### 5.2 根节点切换
1. 当前 root 掉电或断链
2. Mesh 自动选出新 root
3. 新 root 重连 MQTT
4. 前端页面刷新 root 状态
5. 子节点继续保持本地联动

## 6. 业务流程
### 6.1 开灯流程
- Vue 发送开灯命令到 MQTT
- Root 收到命令并转成 Mesh 指令
- 对应节点执行灯效
- 节点回传执行结果
- Root 汇总后上报前端

### 6.2 场景切换流程
- 前端选择场景
- Root 广播场景命令到某个区域或全体节点
- 节点根据场景执行不同灯效
- 形成统一状态回传

### 6.3 断电恢复流程
- 节点重新上电
- 自动加入 Mesh
- Root 重新汇总
- 前端刷新在线状态

## 7. Vue 页面结构
### 7.1 页面建议
- **总览页**：在线节点数、离线数、当前场景、告警数
- **设备页**：每个节点状态、层级、最后心跳
- **分组页**：楼层/区域/会议室控制
- **场景页**：办公、午休、会议、下班
- **日志页**：MQTT 与 Mesh 事件日志

### 7.2 交互建议
- 点击单灯开关
- 区域批量控制
- 全局场景按钮
- 节点详情抽屉
- 故障提示弹窗

## 8. 运行约束
- 供电必须稳定，避免 brownout
- MQTT 连接必须支持自动重连
- Root 切换后要重新建立会话
- UI 不应依赖单一节点在线
- 终端节点应本地自治，不依赖云端实时在线

## 9. OTA 边界

本项目的 OTA 需要分成三类，不能混成一条：

- Mesh 网关：直接走云端 OTA，下发后网关自升级。
- Mesh 灯控节点：由网关作为 Mesh root 下载并分发 OTA，节点本地写入并回滚确认。
- 门铃：走独立 Wi-Fi OTA，不走 Mesh 协议；但它仍然是同一个 App 里的可发现、可配网、可查看设备，现有 App 入口不改。

统一要求：

- 所有可升级设备都要上报 `product_id / hw_version / fw_version / capabilities`。
- 所有可升级设备都要支持 `system.ota`。
- App 里“检查更新”的入口保留在设备详情页，不改变门铃现有发现/配网/查看流程。

### 9.1 Mesh 网关 OTA

- 网关本身具备 Wi-Fi 联网能力，可直接接收 `down/ota`。
- 网关升级成功后，需要继续保持 Mesh root、MQTT、设备状态上报能力。

### 9.2 Mesh 灯控节点 OTA

- 节点不直接对外联网，OTA 由 Mesh root 负责。
- root 下载固件后，通过 Mesh 分发给节点。
- 节点写入后必须做版本回报和回滚确认。

### 9.3 门铃 OTA

- 门铃是独立 Wi-Fi 设备，不进入 Mesh OTA 流程。
- 保留现有 App 中的发现、配网、设备页、视频页与事件页。
- 只补固件 OTA 能力，不改现有用户路径。

## 10. 里程碑拆分
### P0：演示原型
- 三板组网
- 基础开关灯
- 简单状态上报

### P1：业务联动
- MQTT 接入
- Vue 控制台
- 场景切换

### P2：稳定性增强
- Root 切换恢复
- 节点掉线告警
- 重连与心跳

### P3：产品化
- 分组权限
- 定时策略
- 日志审计
- 升级与配置管理

## 10. 验收标准
- 任意一块普通节点掉电后，系统仍可继续工作
- Root 掉电后，Mesh 自动重选新主
- 新 Root 可自动恢复 MQTT 上报
- Vue 页面能实时看到在线状态变化
- 三块板的灯效与业务状态一致

## 11. 实施建议
- 先把 Mesh 网络跑稳，再接 MQTT
- 先做状态上报，再做复杂场景
- 先验证 root 切换，再做产品化 UI
- 保留协议版本号，便于后续扩展
